# 默认采用引导式配置档管理

## 一句话结论

> `clis` 默认提供菜单与逐步输入的引导式操作，参数命令仅服务自动化和脚本调用。

## 上下文链接

- Based on: [[knowledge/cli-profile-scope/content]]

## 上下文

该工具面向需要在 Claude Code 与后续其他 CLI 间管理多套 API 配置的用户。

## 问题

频繁记忆子命令、配置档名称和敏感配置字段会增加日常切换成本，也容易造成参数填写错误。

## 考虑过的替代方案

- 只提供参数化子命令：适合脚本，但不适合日常人工切换。
- 将复制选项混入创建流程：来源语义不明确，操作路径更长。

## 决策

运行 `clis` 后先选择目标 CLI 与五项操作。创建配置档默认通过 API URL、隐藏的 API Key 和模型输入向导完成；JSON 编辑保留为高级入口。复制行为独立成命令和菜单项。

## 结果

交互层需要同时支持终端选择、无回显输入、取消和确认；适配器层应保持可由参数命令调用，以满足自动化需求。

## 探索减负

- 下次可以少问什么：默认交互模式与创建、复制的边界。
- 下次可以少查什么：API URL、API Key 与模型是否应出现在创建向导中。
- 失效条件：目标用户改为完全由 CI 或脚本管理配置，且明确不需要交互式操作。
